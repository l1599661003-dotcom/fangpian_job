# 方片人才管理系统备份、回滚与故障处理手册

更新日期：2026-08-28

## 1. 适用范围

本手册覆盖方片人才管理系统的四类资产：

1. 绑定 Teable Base 中的 86 张固定业务表及其记录。
2. 应用对象存储中的简历、Offer、背调附件、入职资料、测评附件和二维码等文件。
3. 应用源码、锁文件、Dockerfile、构建产物规则和发布配置。
4. `.env.local` 对应的发布 Secret、平台连接器授权及外部系统配置状态。

系统表名是数据锚点。恢复或迁移时不得按日期、人员或环境生成动态表名，不得在源码中写死 `base_id`，不得用新密钥覆盖历史密钥。

## 2. 责任分工

| 角色 | 责任 |
| --- | --- |
| 系统管理员 | 发起备份、确认恢复范围、冻结写入、验收权限与关键数据 |
| 招聘负责人 | 确认招聘需求、人才阶段、Offer 和入职业务数据是否完整 |
| 应用维护人员 | 构建、发布、回滚应用版本，核对健康检查和日志 |
| Studio/Teable 管理员 | 执行 Base 快照或恢复、发布流水线回滚、Secret 注入排查 |
| 企微管理员 | 恢复企业微信机器人、通讯录、日历和会议室授权 |

任何恢复操作至少由系统管理员和业务负责人双人确认。禁止在没有备份点、影响范围和回退方案时直接批量覆盖生产数据。

## 3. 建议恢复目标

以下为首版运行目标，正式上线后应根据业务量重新评审：

- Teable 业务数据：建议每日完整备份，关键发布前额外备份；目标 RPO 不超过 24 小时。
- 简历及业务附件：依赖对象存储版本/生命周期策略；目标 RPO 不超过 24 小时。
- 应用版本：每次生产发布保留可回滚版本；目标 RTO 2 小时。
- 单条误操作：优先使用系统不可变事件、审计日志、合并快照和撤销能力恢复；目标 RTO 30 分钟。

这些目标是运维约定，不代表当前平台已经自动提供对应 SLA。

## 4. 备份清单

### 4.1 发布前必做

1. 记录待发布版本、提交或交付包标识、构建时间和操作人。
2. 运行：

   ```bash
   NODE_OPTIONS=--max-old-space-size=256 pnpm run build
   NODE_OPTIONS=--max-old-space-size=256 node --test tests/*.test.mjs
   pnpm run test:browser
   node --check source-app/resumeflow.js
   git diff --check
   ```

3. 核对 `dist/main.js` 存在，`dist/server/main.js` 不存在。
4. 核对 Docker 运行入口为 `node dist/main.js`。
5. 从 `/api/health/database` 记录期望表数、已初始化表数、缺失表和最近就绪时间。
6. 在 Teable/Studio 管理端创建生产 Base 的备份或导出；导出文件不得放入 Git 仓库。
7. 核对对象存储关键文件能够从系统保存的 CDN 地址读取。
8. 只检查 `.env.local` 中必需键是否存在，不在日志、截图、工单或文档中记录真实值。

### 4.2 定期备份内容

- 所有固定表的表结构、字段类型和记录。
- 简历解析记录、人才主档、应聘记录、阶段事件、审计日志和合并快照。
- 招聘需求、职位、渠道绑定和 RPA 采集任务。
- 测评、约面、面试评价、Offer、背调、入职、离职和回访记录。
- 角色模板、用户、组织、角色授权、敏感字段审批和导出审计。
- 消息模板、触发规则、发送事件和外部同步事件。
- 对象存储文件清单，至少包含对象键、业务对象、上传时间、大小和 CDN 地址。
- 当前应用版本、`package.json`、`pnpm-lock.yaml`、Dockerfile 和构建日志。

## 5. 恢复前决策

恢复前必须填写以下信息：

| 项目 | 内容 |
| --- | --- |
| 故障开始时间 | 精确到分钟 |
| 影响模块 | 人才、招聘、面试、Offer、权限等 |
| 影响记录范围 | 表名、业务 ID、时间段、部门 |
| 最后可信备份点 | 时间、位置、校验结果 |
| 是否冻结写入 | 是/否，开始和解除时间 |
| 恢复方式 | 单条修复、批量恢复、Base 恢复、应用回滚 |
| 审批人 | 系统管理员、业务负责人 |
| 回退条件 | 何种验证失败时撤销本次恢复 |

优先选择影响最小的恢复方式：单条业务撤销 → 指定记录恢复 → 指定表恢复 → 整个 Base 恢复。

## 6. 数据恢复步骤

### 6.1 单条或少量数据

1. 暂停相关人员继续编辑该业务对象。
2. 通过对象级审计、阶段事件、发送事件或同步事件确定最后正确状态。
3. 查重合并错误优先使用系统“撤销合并”，不要手工拆关联记录。
4. Offer、背调、面试评价等已形成不可变历史的对象，不删除历史；新增纠正事件并标明原因和操作人。
5. 恢复后核对主档、应聘记录、阶段事件和关联业务表是否一致。
6. 保存恢复工单、前后值、操作人、审批人和验证结果。

### 6.2 指定表或整个 Base

1. 在 Studio 暂停生产入口或由管理员公告维护窗口，避免恢复过程中继续写入。
2. 先对当前异常数据再做一次保全备份，不能直接覆盖唯一现场。
3. 由 Teable/Studio 管理员在隔离位置恢复备份并校验，不直接把未校验文件导入生产。
4. 校验 86 张固定表、核心字段和记录数量；重点核对人才 ID、应聘记录 ID、需求 ID 和不可变事件链。
5. 需要切换绑定 Base 时由 Studio 平台执行绑定，应用代码不写入 `base_id`。
6. 启动应用后检查 `/api/health` 和 `/api/health/database`，必须达到 `ready` 且 86/86。
7. 依次抽查招聘需求、人才档案、阶段历史、面试、Offer、入职和权限数据。
8. 解除维护窗口后持续观察至少 30 分钟。

## 7. 应用版本回滚

1. 记录当前异常版本、上一稳定版本和回滚原因。
2. 确认数据结构变更是否为向后兼容的增量字段。若新版本已经写入旧版本无法识别的数据，先评估数据兼容，不可盲目回滚。
3. 在 Studio 发布控制台选择上一稳定镜像或版本执行回滚。
4. 回滚后确认容器包含 `dist/main.js`，启动命令为 `node dist/main.js`。
5. 冒烟检查首页、静态 JS/CSS、`/api/health`、`/api/recruitment`、`/api/talents` 和登录权限上下文。
6. 核对最近写入的数据没有因版本回滚丢失。
7. 记录回滚开始、完成时间、操作人、验证人和后续修复计划。

不得用 `git reset --hard`、删除生产表、重建同名表或生成新加密密钥代替正式回滚。

## 8. 常见故障处理

### 8.1 `/api/*` 返回 OSS `NoSuchKey`

含义：请求没有到达 NestJS，而被当成静态对象读取。

处理：

1. 检查生产镜像是否包含 `dist/main.js`。
2. 检查启动命令是否为 `node dist/main.js`。
3. 检查 NestJS 是否与静态前端运行在同一端口、同一进程。
4. 检查前端 API 地址是否使用当前预览子路径作为基准。
5. 修复后要求 `/api/recruitment` 返回 JSON，不接受前端兜底掩盖。

### 8.2 健康检查 `degraded`、业务接口 503

含义：NestJS 已启动，但 Teable 尚未就绪。

处理：

1. 查看 `/api/health/database` 的错误、缺失表和重试次数。
2. 检查 `STUDIO_PLATFORM_URL`、`STUDIO_APP_TOKEN` 和绑定 Base 注入链路；只报告缺失，不生成替代值。
3. 确认平台 SDK 可访问绑定 Base。
4. 使用健康接口的手动重试能力后观察是否恢复为 86/86。
5. 持续失败时交由 Studio 平台排查令牌或 Base 绑定。

### 8.3 LLM 返回 401 或简历仅规则抽取

1. 检查应用进程是否实际收到 `STUDIO_APP_TOKEN`，不要只看当前终端环境。
2. 不生成新 Token，不把 Token 写入源码或 `.env.example`。
3. 确认调用路径是平台 `/llm/v1/chat/completions` 封装，而不是外部直连。
4. LLM 不可用时允许规则抽取降级，但页面必须显示真实状态，AI 结果仍需人工确认。

### 8.4 OCR 或对象存储失败

1. 先请求签名上传 URL，验证 PUT 和 CDN GET。
2. 核对文件类型、大小和对象键，不在数据库保存本地临时路径。
3. OCR 必须通过 `server/platform/mcp.ts` 的 `ocr.recognize()`。
4. OCR 失败保留原文件、任务错误和重试入口，不把空文本标记为解析成功。

### 8.5 企业微信连接失败

1. 读取 `/api/messages/connection` 的错误码和授权指引。
2. `850003 authorization expired` 表示机器人业务授权过期，由机器人创建者在企业微信重新授权；不是重新生成应用密钥。
3. “找不到凭证持有人”或“未绑定”由应用主人在当前环境的“个人中心 → MCP市场”绑定企业微信连接器。
4. 发送、日历或会议室同步失败时保留本地记录并标记失败，只有失败记录允许人工重试。
5. 未获得明确外部成功响应时不得展示“已发送”或“已预约”。

### 8.6 当前用户始终未登录或权限不生效

1. 检查 `/api/access/me` 的 `identitySource` 和 `enforcement`。
2. 确认 Studio 反代实际注入的可信用户 ID、姓名头名称。
3. 在环境变量中配置对应头名后切换 `ACCESS_CONTROL_MODE=strict`。
4. 生产环境不得启用浏览器可伪造的开发身份头。
5. 修改角色后重新请求接口，确认撤销和过期授权立即失效。

### 8.7 后台任务长时间运行或失败

1. 通过任务 ID 查询状态、进度和错误。
2. 不在同步 HTTP 请求中等待 OCR、批量抓取或长耗时转写。
3. 确认任务没有重复执行同一业务幂等键。
4. 失败后保留原始文件、输入摘要和错误，允许人工重试；不要静默吞错。

## 9. 恢复后验收

恢复或回滚完成后至少验证：

- `/api/health` 为 `ok`，数据库为 `ready`，固定表 86/86。
- 首页、JS、CSS 和核心 API 无 404/5xx。
- 招聘需求可创建、读取和关闭。
- 人才列表、人才详情、阶段时间线和去重案件可读取。
- 角色数据范围、敏感字段脱敏和导出水印仍生效。
- 对象存储上传及 CDN 读取正常。
- LLM/OCR 按实际状态成功或明确降级。
- 企业微信、会议室和通知不伪造成功状态。
- 桌面端和 390px 移动端无页面级横向溢出。
